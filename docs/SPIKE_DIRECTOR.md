# L3 可行性测试 · AI 剧情导演（spike）

> 目标：在投入事件系统开发前，验证**核心假设**——DeepSeek v4 flash 能否在预制事件池中编排剧情走向：每次游玩不同、不脱轨、自然走向结局。

## ✅ 测试结果（2026-07）：达标，L3 机制成立

| 指标 | 目标 | v1（[事件] 标记协议） | v2（编号选择协议） |
|---|---|---|---|
| 不同事件序列 | ≥3 种 | 不可信（7/11 步随机兜底） | **5/5 全不同** |
| 自然走到结局 | ≥70% | 1/1（巧合，无效） | **5/5（100%）** |
| 格式失败/局 | ≤1 | 7 | **0**（1 次重试救回） |

**结论**：v2 协议（编号选择 + 只列可选事件 + 失败重试）下，v4 flash 能稳定编排事件池、每局序列不同、自然收束到结局。**L3「AI 导演」机制成立，按 v2 协议纳入 M4 事件系统设计**（决策 D47/D48）。

**剩余观察（M4 设计要点）**：
1. 9 事件小池子下每局会用尽全部事件——多样性来自顺序 + AI 台词 + 玩家选择，对 30 分钟 Demo 可接受；
2. 结局事件在"已见光"后仍可选"平静结局"（前提不互斥）——正式版结局前置条件应互斥或措辞自洽；
3. 导演暂未接入玩家选择影响——玩家-导演联动留待 M3/M4 验证。

## 为什么先做这个

L3「AI 决定主线」是你们愿景中最激进的部分，也是风险最高的假设：
- AI 会不会乱选事件（违反前置条件）？
- 会不会编造不存在的 id / 剧情？
- 能不能自己编排节奏、自然收束到结局？
- 多局之间是不是真的"每次都不一样"？

如果这个机制不成立，L1/L2 做得再好，核心卖点也打折——所以**先用 20 分钟把它验证掉**，再决定事件系统怎么设计。这正是"先验证风险最高的部分"。

## 测试方法（spike/director-test.html）

1. 浏览器打开 `spike/director-test.html`，填桌面 `API.txt` 的 key。
2. 点「跑 5 局对比」。
3. 读日志与汇总。

**测试内容**：
- 内置事件池 11 个：9 个普通事件（含 3 条线索链：老周-光、陈婆婆-长椅、苏黎-邀请函）+ 2 个结局。
- 每局 = 导演反复选事件（最多 15 步），游戏状态（flag 标记）自动维护。
- 统计每局：事件序列、结局、违规次数、兜底次数、未解析次数。

## 成功标准（达标即证明 L3 机制可行）

| 指标 | 目标 |
|---|---|
| 不同事件序列数（5 局） | ≥ 3 种（证明"每次不一样"） |
| 自然走到结局 | ≥ 70%（4/5 局） |
| 每局违规（前置不符/非法 id/未解析/兜底） | ≤ 1 次 |
| 旁白质量 | 人工抽查：衔接自然、不剧透、不崩人设 |

## 结果解读

**✅ 达标** → L3 架构成立，后续 M4 事件系统按"事件池 + AI 导演"设计：
- 事件脚本字段沿用测试池结构（requires / requiresAny / minEvents / sets / ending）
- 真实游戏中，导演提示词还要并入：当前剧情状态 + 最近对话摘要 + 玩家好感度

**⚠️ 部分不达标**（序列多样但违规偏多）→ 先修提示词再测：
- 收紧规则描述、把事件池改编号而非 id、增加 few-shot 示例（给一个"理想选择"的例子）
- 或给"导演"限定候选（只把满足前置的事件放进提示词，从源头杜绝违规——工程兜底，正式版推荐这么做）

**❌ 严重不达标**（选不出结局/大量编造）→ 降级方案：
- 回到 L2：AI 只写台词，事件顺序由人工脚本硬编（你们 8-12 个事件线性排布）
- 或"半 AI"：前 2 个事件固定，AI 只调度后半段

## 成本参考

每局约 6-10 次调用，5 局 ≈ 4-5 万 tokens，成本约 0.05-0.1 元，可放心跑。

## 测试后的动作

- 结果与你的观察（哪局最像"真游戏"、哪局最崩）记入 `docs/AI_ISSUES.md`。
- 达标 → 我在 M2 对话 UI 里就把导演模块的接口定好（`Director.chooseNext(state, pool)`）。
- 不达标 → 按上面降级方案调整 L3 目标，并把结论更新到 DESIGN.md 第 6 节。
